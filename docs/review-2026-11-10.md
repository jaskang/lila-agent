# 独立重评：结论与差异（2026-11-10）

做法：先不看任何现有文档和代码，只凭四篇参考文章（Subagents、Dynamic workflows、Super-agent、Critical thinking）从零推导产品定位和架构，再回头对照 `product-v3.md`、`HANDOFF.md` 和 `lila-core` / `lila-agent`。

## 结论

**不重新设计，不出 architecture-v4。** 从零推导的结果和现有设计在主干上一致：

| 从零推导出的 | 现状 |
|---|---|
| 任务是一等公民，会话隐藏 | 请求为中心的主界面（product-v3 §3） |
| Router 只路由不执行，靠收窄工具强制 | PM 的 `[tools]` 由 CLI 限制，只能读和跑 `lila` |
| 流程由确定性代码推进 | lilad 的 flow：实现 → 检查 → 验证 → 返工 |
| 目标和约束存在会话之外 | `Brief`：原话、验收标准、不做什么，每一步原样附上 |
| 报告列出假设和未验证项 | `Outcome`：decisions、unverified、verdict |
| 换一家模型做验证 | 默认 tester 是 Codex，engineer 是 Claude |
| 事件直通，Router 只收一行摘要 | `route.rs`，完成通知只给在等的人 |
| 适配器声明能力，核心按能力降级 | `Caps`、`AgentEvent`、`Command` |
| Watchdog、预算、worktree 隔离 | `watch.rs`、`--budget`、worktree 槽 |

两次独立推导收敛到同一个设计，说明架构方向可以定下来了。继续对照这四篇文章重评，收益很低。

## 重评中我提过、现在收回的

- **低风险任务自动验收。** 交付是直接落到主分支的提交，验收是唯一的责任点，"改代码的都要过你"应当保留。该做的是让验收更省力，而不是跳过。
- **事件溯源（所有状态从事件日志重放）。** 现有的状态表加 `task_events` 已经够用，改造没有用户价值。
- **用模型判断是否偏离目标。** 每一步都重新附上原话，tester 按原话验证，已经覆盖了大部分漂移；再加一个定时的模型判断只是多花额度。
- **按完成标准逐条挂检查命令。** 一条项目级 `check` 够用。

## 真正的差异，按价值排序

1. **验收标准是软约束。** 现在只在 PM 的提示词里要求写 `--accept`，lilad 不拦（`requests.rs` 直接收下空的 `accept`）。建议：PM 发起、走 `code` 流程的任务，没有 `--accept` 就拒绝，错误信息提示它先问人一个问题。用户直接派的任务不受影响，原话就是标准。
2. **验证者异厂商是默认值，不是规则。** 用户把 tester 改成 Claude 时没有任何提示。建议：流程里 verify 步骤的成员与 implement 步骤的成员同厂商时，在项目设置和验收卡片上标一句"同源验证"。不强制，因为用户可能只有一家订阅。
3. **验证结论没有落到每条标准上。** tester 只给整体 pass / fail。建议：`--verdict` 之外允许逐条 `--met "<标准>"` / `--unmet "<标准>"`，验收卡片按标准列出。这一条等前两条用过再定。
4. **默认团队偏大。** 五个角色里 designer 和 architect 是人设，不是结构上必需的；文章②明确说普通编码任务不需要评审团，单个 Claude 会话内部也有原生 subagent。建议：新建项目默认只勾助理、engineer、tester，另外两个保留为可选。

## 更重要的判断：现在的风险不在架构

- 四个工作日 95 个提交，M1、M2 和运行时 v3 的 P0–P4 全部落地，测试 247 个。
- 两次真跑各暴露了 3 个和 5 个只有真实 agent 才会出现的问题（并发验收合并失败、Codex 交了任务还在转、助理一次只能收一件、重启后忘记问过）。
- `HANDOFF.md` 的"等用户亲手验证"还有一长串：会话续接、账号切换、窗口交互、终端输入。

结论：自动化测试覆盖不到的问题密度还很高，功能面已经超出被真实使用验证过的范围。

## 建议的下一步

1. **冻结架构和新功能，先自用一周。** 拿一个真实项目，每天用 Lila 做真实需求，只修用出来的问题。M3（往来同步）和 M4（Asana）暂缓。
2. **自用期间只做差异 1 和 2。** 都是小改动，直接提高每次交付的可信度。
3. **一周后用数据决定去留**：验收打回率、你推翻分拣的比例、每件请求的额度消耗、哪些角色和运行时真的用到了。没用到的（可能包括 designer、architect、omp）从默认配置里拿掉。

## 记录：差异 1 和 2（2026-11-10 完成）

- **验收标准成了硬约束。** 成员（实际上是助理）发起、以验证结束的流程（默认的 `code`），自己和上面的任务都没有 `--accept` 时，`lila task new` 拒绝，并提示补标准、先问人一个问题，或者小改动走 `--flow quick`。你直接派的任务、`quick`、`--flow none`、不进流程的派活都不受影响。助理的提示词同步说明了这条。
- **同源验证会标出来。** 流程里给结论的成员和被它验证的成员用同一家模型时（Claude 对 Claude、Codex 对 Codex；omp 按模型名比），验收卡片在验证那一步下面多一行「同源验证：tester 和 engineer 是同一家模型」，项目设置的成员列表里该成员的角色名后面有黄色的「同源验证」，换模型时立即跟着变。不拦。
- 代码：`flow::self_verified`、`config::model_source`、`Team::{source_of, self_verified, is_verified}`、`daemon/requests.rs`（`task_new`）、`daemon/review.rs`（`add_review`）、`inbox::same_source`、`lila-app/src/settings.rs`。
- 验证：新增 3 个测试，工作区 274 个全过，Clippy 零警告；设置页的标记截图看过。**没有真跑**：助理被拒后会不会顺利补上标准，要在真实会话里看。
