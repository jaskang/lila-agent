# M1 实测记录：编排核心

> 2026-11-05 · 真实环境：hc 0.1.18、Claude Code 2.1.318、codex-cli 0.166.0。
> 为节省额度：团队只有 owner / engineer / tester；Claude 成员用 `claude-haiku-5-5`，Codex 用 `gpt-6.1-sol` + `effort=low`；全部放在隔离的 `LILA_HOME` 里。

## 交付内容

- `lila` CLI：`init / roles / up / down / status / task (new|start|done|block|cancel|show|ls) / ask / inbox / answer / log / pause / resume / daemon`，以及 `--skill`、`--json`。
- `lilad`：运行在 herdr-core 终端里，是状态的唯一写入方。它订阅 hc 事件，按成员排队派发任务，转发完成和阻塞通知，管理收件箱，并负责启动超时检测、沉默提醒和成员退出处理。
- 4 个默认角色（`defaults/roles/`），角色提示词和协议段分开：协议段由 Lila 根据团队自动生成。
- 54 个测试：
  - `lila-core` 23 个：状态机、指派规则、提示词、命令生成、派发和沉默判定。
  - `lila-store` 6 个。
  - `lila` 25 个：其中 lilad 的 18 个用假终端跑完整流程。

| 3 | 加 `multiply` | ✅ engineer 发现约束冲突后 `block`，Owner 自己做了决定，没有打扰你；此后没有重复派活 | ③ 任务排队 5 分钟没发出去：hc 的 `send if=` 只接受 `idle`/`working`，lilad 却传了 `done` → `done` 状态投递时不加条件；假终端照 hc 的规则校验；同一投递错误只记一次日志。重启 lilad 后，正在运行的成员被正确接管，排队任务也补发了 |

另外修复了 1 个竞态问题：守护进程启动时拿到的快照早于成员启动，导致刚启动的成员被误判为"已退出" → 对账时跳过快照之后才启动的成员。

## 验证过的机制

- 启动 20 秒内没有状态上报 → 收件箱出现 `startup` 提醒；成员第一次上报状态后自动消失。Claude Code 和 Codex 都会弹目录信任对话框。
- Codex 弹审批时状态为 `blocked`、`kind=permission`（`msg` 为空）→ 收件箱出现 `terminal` 提醒；状态离开 `blocked` 后自动消失。
- 沉默提醒：Owner 空闲 5 分钟且有未关闭的任务 → 收到 `<lila note>` 提醒 → 它检查状态后关单。
- 交给你的任务完成后 → 收件箱出现 `report`，`lila answer Qn` 关闭这条提醒。
- `lila down` 正常停止成员，不产生误报；`lila daemon stop` 后成员继续运行，lilad 重启后会接管它们。

## 待办

1. ✅ **修改已派出的任务**：`lila task edit T10 [--title] [--body|--body-file] [--append]`。任务还在排队时直接改写；已经投递的只能 `--append`，补充内容会作为 `<lila note>` 发给对方，同时追加到任务文件里。可以编辑的人：你、Owner、派这个任务的人。协议段要求用 edit 修正任务，不要另开一个修正任务。
2. ✅ **Codex 不开网络也能用**：`lila` 连 socket 被沙箱拦截（EPERM）时，改为通过项目里的 `.lila/spool/` 收发文件（`<id>.req.json` → `<id>.reply.json`，先写临时文件再 rename）。lilad 每 250ms 检查一次，60 秒没有回复则撤回请求并报错。成员的环境里会带上 `LILA_ROOT`。默认 tester 角色已去掉 `network_access`。
3. ✅ **来回修复的轮数上限**：`settings.max_rounds`（默认 3）。同一对成员在一条任务链上连续来回（engineer → tester → engineer 算一轮）超过上限后，`lila task new` 会拒绝，并提示用 `lila task block` 交给 Owner 决定。换一对成员（比如 Owner 重新规划）则重新计数。
4. **上下文膨胀**：成员长期在线，4 轮之后还没问题；任务多了以后需要 `/compact` 或每个任务开新会话（M3）。
5. **订阅额度用完**：仍未遇到，遇到时记录 CLI 上报的状态。
